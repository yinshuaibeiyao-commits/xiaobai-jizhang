# security-audit — 安全审计

对代码做安全审计，输出审计报告。默认**只审计、不改动**代码；仅当用户明确要求「修复」时才改源码。

## 执行步骤

### 1. 确定审计范围

- 用户指定了文件 / 目录 → 只查该范围。
- 否则扫描整个项目源码与配置文件，排除 `node_modules`、`out/`、`dist/`、`coverage/`、`*.test.ts`、`package-lock.json` 等锁文件与生成产物。

### 2. 按四类风险检查

#### ① 敏感信息硬编码泄露

- 密码、API key、token、secret、私钥、数据库连接串、AccessKey/SecretKey、口令等是否硬编码在源码里。
- 排查手段：搜索常见关键词（`password`、`passwd`、`secret`、`token`、`api_key`、`apikey`、`access_key`、`private key`、`Bearer`、`AKIA` 等），以及直接字符串常量、`=== 'xxx'` 比较中的可疑值。
- **注意区分**：测试文件里的假数据、示例值、占位符不算真实泄露，但要单独标注「疑似/示例」，不要误报。

#### ② 注入漏洞

- **SQL 注入**：字符串拼接 SQL、未参数化的查询。（本项目当前用 JSON 文件存储，无 SQL；若未来接入数据库同样要查——报告里注明「当前无 SQL 代码」即可。）
- **XSS**：renderer 里 `dangerouslySetInnerHTML`、`innerHTML` 拼接、未转义地把用户输入注入 DOM。
- **命令注入**：`child_process.exec` / `spawn` 拼接用户输入、`shell: true` 的使用。
- **路径 / URL 注入**：用户输入未经校验直接拼进文件路径、`loadURL`、`openExternal` 等。

#### ③ 配置文件明文敏感信息

- 检查 `.npmrc`、`package.json`、`electron-builder.yml`、`.env`、`electron.vite.config.ts` 等配置里是否有明文密码 / token / 密钥 / 内网地址 / 私钥。
- 检查 `.gitignore` 是否已排除 `.env`、密钥文件、证书、私钥等（否则会被提交进仓库）。

#### ④ 其它安全隐患

- **路径遍历**：文件读写路径由用户输入拼接且未校验（例如后续对 `dataPath`、导入导出路径的处理）。
- **不安全的动态执行**：`eval`、`new Function` 执行不可信输入。
- **弱加密 / 弱随机**：`Math.random()` 用于安全场景、明文存储密码、用可逆或弱算法加密敏感数据。
- **日志泄露**：把密码 / token / 完整用户数据打进 `console.log` 或日志文件。
- **越权 / 缺校验**：IPC handler 未校验输入、缺失权限 / 鉴权检查。
- **Electron 配置不当**：`nodeIntegration: true`、`contextIsolation: false`、`sandbox: false`、`webSecurity: false`，以及 `shell.openExternal` 未校验 URL 协议（只允许 http/https）。
- **依赖漏洞**：`package.json` 里的已知高危依赖版本（可用 `npm audit` 佐证，但不要擅自运行破坏性修复）。

### 3. 输出审计报告

汇总写入项目根目录 `SECURITY_REPORT.md`，按严重程度分级（严重 / 高 / 中 / 低），结构如下，用中文填写：

```markdown
# 安全审计报告

- 生成时间：<日期>
- 审计范围：<文件 / 目录>

## 审计项
1. 敏感信息硬编码泄露
2. 注入漏洞（SQL / XSS / 命令 / 路径）
3. 配置文件明文敏感信息
4. 其它安全隐患（路径遍历、反序列化、弱加密、日志、越权、Electron 配置、依赖）

## 结果总览
- 审计文件 N 个，发现问题 M 个（严重 A / 高 B / 中 C / 低 D）

## 问题明细（按严重程度排序）
- 每个问题：文件路径 + 行号 + 严重度 + 类别 + 问题说明 + 修复建议

## 结论
- 一句话总结安全状况，列出最需要优先处理的问题。
```

- 同时在终端向用户简述结果。

### 4. 若用户要求修复

- 仅在用户明确说「修复 / 改」时才改代码，逐条修复并在报告里把对应问题标记为「已修复」。

## 注意事项

- 默认只审计、不改代码；修复需用户明确授权。
- 严重程度要客观：能实际利用、影响大 → 严重/高；理论风险、影响小 → 中/低。
- 每条问题都要给出**文件 + 行号 + 修复建议**，不要只写「有安全风险」这类空话。
- 只审计本项目代码，**不做任何攻击 / 利用验证，不访问外部系统，不尝试读取本机真实凭据**。
- 区分「真实泄露」与「测试假数据 / 示例值」，拿不准就标「疑似」并说明理由，避免误报。
