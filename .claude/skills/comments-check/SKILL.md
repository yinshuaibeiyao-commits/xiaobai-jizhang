# comments-check — 注释检查

检查代码注释的三方面质量，输出检查报告。默认**只检查、不改动**代码；只有当用户明确要求「补注释 / 修注释」时才允许修改源码。

## 执行步骤

### 1. 确定检查范围

- 用户指定了文件 / 目录 → 只查该范围。
- 否则扫描 `src/**` 下的源码（`.ts` / `.tsx`），排除 `*.test.ts`、纯类型定义（`types.ts`）、第三方生成代码与 `node_modules`。

### 2. 按三项标准检查

#### ① 注释是否缺失（密度）

- **每个函数 / 方法 / 类**都要有注释，说清「做什么、为什么、关键入参与返回值」。
- **每处重要核心逻辑**（分支判断、算法、易错点、魔法数字、业务规则）要有行内注释。
- 粗略密度参考：注释与代码约 **3 : 7**（约 30% 注释行）。这是方向性目标，不是逐 10 行机械计数；以「是否覆盖关键点」为主、「密度比例」为辅来判定。
- 判定为「缺失」的情形：函数完全没有注释、核心逻辑无任何说明、注释密度明显偏低。

#### ② 注释与代码是否匹配

- 逐条对照注释描述与代码实际行为，检查：
  - 注释是否描述了代码**真正在做的事**；
  - 是否**过时**（代码已改、注释未同步）；
  - 是否**张冠李戴**（复制粘贴错位、指代错误变量 / 字段）；
  - 是否与常量、默认值、条件边界**不一致**。

#### ③ 是否符合小白视角（可读性）

- 注释应通俗易懂，让非技术用户也能看懂，避免只有资深开发者才懂的术语、缩写、黑话。
- 尽量写「为什么这么做」和「对用户意味着什么」，而非复述代码本身。
- 判定为「难懂」的情形：出现未解释的术语 / 缩写、只复述代码没讲清意图、句子晦涩。

### 3. 输出检查报告

汇总写入项目根目录 `COMMENTS_REPORT.md`，结构如下，并用中文填写：

```markdown
# 注释检查报告

- 生成时间：<日期>
- 检查范围：<文件 / 目录>

## 检查标准
1. 注释缺失：每个函数与核心逻辑都要有详细注释，注释与代码约 3:7。
2. 注释匹配：注释内容与实际代码一致、不过时、不张冠李戴。
3. 小白视角：注释通俗易懂，非技术用户能读懂。

## 结果总览
- 检查文件 N 个，发现问题 M 个（缺失 X / 不匹配 Y / 难懂 Z）

## 问题明细（按严重程度排序）
- 每个问题：文件路径 + 行号 + 类别（缺失 / 不匹配 / 难懂）+ 问题说明 + 修改建议

## 结论
- 一句话总结注释质量，列出最需要优先处理的问题。
```

- 同时在终端向用户简述结果。

## 注意事项

- 默认只检查、不改代码；只有用户明确说「补注释 / 修注释」才可改动源码。
- 「3:7」是参考密度，不要为了凑比例而添加无意义注释；注释质量比数量重要。
- 判断「匹配」和「难懂」时若拿不准，标注为「疑似」并给出理由，不要武断下结论。
- 报告要给出**具体行号**和**可操作建议**，不要只写「注释较少」这类空话。
